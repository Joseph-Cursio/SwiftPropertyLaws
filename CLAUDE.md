# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

**Per-type module provenance closes the import gap (2026-08-08).** `--context-files` told the scan which types *exist*; it never said which module to `import` for them, so a suite for a type this target merely extends still could not name it — the `@testable import <Target>` defect, one module over. Context entries are now attributed `Module=path` (a bare path stays unattributed, and the split only applies when the prefix looks like a module name, because a path may legitimately contain `=`). `TypeShape`'s aggregate records the module whose context files carried the **primary declaration**, and the emitter writes a plain `import` for each.

**Plain, not `@testable`, and that forced a second rule.** `@testable` is emitted for the scanned target alone: across a package boundary it needs the dependency built with testability, which is not ours to assume. So a foreign type is reachable only through its public API, and a foreign `internal` type is out of reach however the imports are written — new `SkippedType.Reason.foreignNonPublic(module)` drops those rather than trading one uncompilable emission for another. It fired zero times on swift-syntax (everything `SwiftParser` extends is public), so it is guarded by unit tests rather than corpus evidence.

**`--extra-import <Module>` is the opt-in half**, for a package that *supplies* generators rather than declaring types — `--extra-import PropertyLawSyntax` so an emitted `Syntax.gen()` resolves. Deliberately not inferred: an opt-in product's import would break every project that has the type and not the dependency.

Verified end-to-end on `SwiftParser`: `@testable import SwiftParser`, `import SwiftSyntax`, `import PropertyLawSyntax`. Guarded by `ModuleProvenanceTests` (13); mutation-tested, 6 mutants, 6 killed — two survived first and both were real gaps: a name declared in *both* target and context kept its foreign attribution (hidden because the test used the target's own module name, which the self-import guard filters anyway), and nothing asserted that `--extra-import <the target itself>` is filtered out.

**v2.6.0 opt-in `PropertyLawSyntax` product — `Gen<Syntax>` (2026-08-08).** `Syntax` was the single largest derivation gap in the swift.org corpus: **303 of the scaffolded placeholder slots ask for a `Generator<Syntax, _>`**, because its stored properties are an opaque arena (`SyntaxDataArena`, `SyntaxDataReference`) that no tier can construct. Fourth opt-in product, same posture as `PropertyLawComplex` / `PropertyLawCollections` / `PropertyLawAsync`: `swift-syntax` was already a dependency of the macro, the plugin and three test targets, but **this is the first shipped library to link `SwiftParser`**, and the product is opt-in precisely so that choice stays local. Parsing rather than hand-built nodes because fourteen source templates parse into hundreds of real nodes across dozens of kinds; assembling that from generated initializers would be bespoke code per kind, with synthetic trivia.

**The design took three attempts, and the first two were wrong in ways only measurement caught.** `Syntax.==` and `hashValue` are both `SyntaxIdentifier`, and swift-syntax notes that *"lhs and rhs might have the same contents even if their IDs are different"*.

1. **A fixed 32-node pool**, so repeats made the Equatable antecedent fire. It failed `Hashable.distribution` against correct code — *"1000 samples produced only 32 unique hashValues (ratio 0.032)"* under a 0.10 threshold — which is the `BitSet.Counted` false-refutation mode. Rejected on the reasoning that *any* fixed pool caps unique hashes at its size against a budget-sized denominator.
2. **A fresh tree parsed per draw.** That reasoning was right about the cap and wrong about the alternative. Identity keys on **structural position**, so 100 sources of identical shape and wholly different tokens produced *one* distinct id — the per-draw discriminator created no identities at all. Varying the shape did not rescue it either, because the id is tied to the tree's **arena**, freed the moment the tree is dropped and its address reused: **300 parsed-and-dropped trees yielded 78 unique ids**, and the generator gave 751 in 10 000 draws — ratio 0.075, *failing at `.exhaustive` the same law attempt 1 was rejected for*. The shipped doc comment claimed "healthy at any budget"; it was false, and the tests only ran to 2 000 so nothing caught it.
3. **A large pool whose trees stay alive.** The same 300 trees, retained, give **11 700 unique ids from 11 700 nodes** — one identity per node. Identity is available exactly as long as the arena is.

So the pool was right and the reason for rejecting it was wrong: a pool caps identities at its size, but the alternative capped them *lower*. Sizing is the whole game — `distribution` needs `poolSize > budget / 10`, so `defaultPoolSize` is 4 096 and the built pool is 5 520 nodes, giving **ratio 0.372 at 10 000 draws** where the previous design gave 0.075. Pool trees are runs of 1–12 statements mixed across templates, because same-shaped trees contribute far fewer identities than they do nodes.

**The typed generators draw from the same retained pool**, filtered once at construction. That replaced a per-draw parse whose trees were dropped — the same identity bug one level down — and made the target **6× faster** (34.5s → 5.2s) rather than slower. The per-draw template rotation is gone with it: filtering the whole pool reaches a type present in *any* tree, which is strictly stronger.

The cost, stated plainly: `a == b` between two draws happens at `1 / poolSize`, so the Equatable laws needing an equal pair are close to vacuous. Over identity equality those are theorems about `SyntaxIdentifier` rather than risks, and reflexivity still covers "the same node compares equal and hashes the same". `pooled(size:)` remains for a caller who wants the antecedent to fire and will accept the distribution violation that comes with it.

**Downstream demand, acted on.** SwiftInferProperties measured six concrete node types blocking its verification: `DeclModifierListSyntax`, `StringLiteralExprSyntax`, `InheritanceClauseSyntax`, `DictionaryExprSyntax`, `CodeBlockItemSyntax`, `ArraySlice<CodeBlockItemSyntax>`. Four were already reachable through the generic `Gen<T>.syntaxNode()` — the payoff for writing it generically instead of by hand. `DictionaryExprSyntax` needed template 14 (no template contained a dictionary literal). `ArraySlice<CodeBlockItemSyntax>` is not a `SyntaxProtocol` at all, so it was handled in the kit's `CompositeMemberParser` as a new `GeneratorPlan.arraySlice` case — **general rather than syntax-specific**, since `ArraySlice` is stdlib and every element type gains. A distinct plan case rather than a spelling of `.array`, because a member declared `ArraySlice<T>` will not accept `[T]`.

**A trailing marker on the `.todo` arm.** `.userGen` and `.todo` rendered identically as `Foo.gen()`, so a reader could not tell a working generator from a deliberate compile error — and neither could a grep: a survey earlier in this session counted `.userGen` entries as unresolved for exactly that reason. `.todo` now ends in `// TODO: no generator derived — supply \`static func gen()\` (this line will not compile)`. A trailing line comment is safe only because `.todo` reaches the emitter from two callers that both put the expression last on its line — `GeneratorResolver` and `ScaffoldEmitter` `return nil` on `.todo` before splicing anything. `EmittedFileParsesTests` parses whole emitted files with SwiftParser to keep that true rather than assumed, and mutants that break the marker into non-comment or unterminated-block forms are caught by it.

**`static func gen()` on the node types is what actually closes the corpus slots, with no emitter change.** `GeneratorExpressionEmitter` renders a `.todo` as `"\(typeName).gen()"` — the same spelling PRD §5.7's Strategy A uses — so a generated suite already read `using: Syntax.gen()` and merely lacked the method. `PropertyLawSyntax` now declares it on `Syntax` and the six base node types. **Deliberately not entries in `CompositeMemberParser.knownValueGenerator`**, which is how `UUID` and `Date` resolve: that path also makes the emitter write `import PropertyLawSyntax`, and unlike Foundation this product is opt-in, so the import would break every project with a `Syntax`-typed member and no dependency on it — turning a clear "provide a `gen()`" diagnostic into an obscure "no such module". Shipping the method means a project that *has* the product gets working code and one that doesn't sees no change. The generated file still needs the import, which is the same per-type module-provenance gap as the foreign-type problem.

**`Unicode.Scalar` added to the kit's general value-type table** (`Gen<Unicode.Scalar>.unicodeScalar()` in a new `StdlibGenerators.swift`) — the only *stdlib* enum-payload blocker in the corpus tail, and a general win rather than a swift-syntax one: `Character` was already in the table and its scalar sibling was not. Banded rather than uniform (ASCII 4, Latin 2, low-BMP 2, high-BMP 1, astral 1), because a uniform draw over `0 ... 0x10FFFF` is ~97% unassigned planes 3–13, putting every boundary that actually breaks text code out of reach. **A mutant widening a band into the surrogate range survived**, because the original `?? U+FFFD` fallback quietly rewrote each invalid draw instead of failing — so the fallback is now a `preconditionFailure` naming the offending band. Same class as every other finding in this file: a default presented as a guarantee. `SyntaxText`, `RawTokenSyntax` and `RawExprSyntax` stay declined as `@_spi(RawSyntax)`; `ParsableCommand.Type` / `Macro.Type` are metatypes and `Error` / `CodingKey` existentials, none of which have values to draw.

**Cost.** Parsing per draw made `PropertyLawSyntaxTests` the slowest target in the repo — 17s before trimming. The law-suite tests now run at `.sanity` except one kept at `.standard` as the realistic-budget proof, and the distribution sweep caps at 2 000 trials rather than 5 000; the target is ~13s and the full suite ~13s. Budget-independence is pinned by `discriminatorVariesTheTree`, not by the ratio sweep — a ratio at any single size cannot establish it, which is exactly what the surviving mutant showed.

**`Gen<T>.syntaxNode()` generalises it to every typed node** — `ExprSyntax` (34 corpus slots), `TokenSyntax` (5), `DeclSyntax`, `StmtSyntax`, `PatternSyntax`, `TypeSyntax` and the ~300 concrete node structs. They are the same parsed tree filtered by `Syntax.as(T.self)`, so writing the three that the corpus named by hand would have left the siblings still asking, for no saving. The search **rotates through templates** when the drawn one has no node of that type (`PatternSyntax` is absent from `let x = 1` but present in the `guard let` and `for … in` shapes); a type absent from every template hits a `preconditionFailure` naming it, which is a visible boundary rather than a substituted node of the wrong kind.

**`RawTokenSyntax` is deliberately not shipped.** It is `@_spi(RawSyntax)` with an internal initializer, so a generator would put `@_spi(RawSyntax) import SwiftSyntax` in a library's surface and pin this package to an interface upstream reserves the right to break. Its corpus slots come from swift-syntax's own parser internals, which its own suite covers with that SPI.

**A mutant found the distribution tests were weaker than their claim.** Pinning the per-draw discriminator to a constant survived them: the 14 templates alone parse to >500 distinct nodes, which clears the 0.10 threshold at every budget the ratio tests used, so they were not actually testing budget-independence — the property the whole design rests on. Fixed by asserting the mechanism directly (distinct *trees* must outnumber the templates) rather than inferring it from a ratio. 12 mutants across both files, 12 killed.

16 tests in `SyntaxGeneratorTests` and 12 in `SyntaxNodeGeneratorTests`, including the distribution guard at 100 / 1 000 / 5 000 trials, the all-distinct assertion (which fails if the default silently becomes a pool again), node-kind spread, index wrapping, seeded replay, and the two law suites the plugin actually emits for `Syntax` — both now green.

**`--context-files`: the scan can read its dependencies' sources (2026-08-08).** The `declaration not in this target` bucket below was not a fact about those types — it was a fact about what the scan had been shown. A per-target run sees `AccessorBlockSyntax` only *extended*, never declared, so it knows no members, no initializers, not even the kind. **Measured on swift-syntax: `SwiftParser` scanned alone reported 114 of its 199 detected types that way; handed its dependencies as context, 9** (the rest being stdlib and out-of-scan modules), and derived generators over the same run went **1 → 6**. Those 105 moved into accurate buckets — mostly `user-defined init`, which is the truth about them.

**Merging the two file lists would be the wrong fix**, and is why this is a second flag rather than "pass more files": a merged scan also *emits* a suite for every dependency type, so `SwiftParser`'s generated file carries 842 suites instead of 199 and duplicates everything `SwiftSyntax`'s own run already emits. Context is for **knowing**, not for testing. `TypeAggregate.seenInTarget` latches on any target-file mention, and only those become entries — a context-only type is neither emitted nor reported as skipped, because it was never a candidate. Context files are walked **first**, which is load-bearing when a name is declared on both sides: `record` lets the last non-empty member list win, so target-last means the target's own declaration survives.

The plugin walks `Target.dependencies` transitively (deduped and sorted — a diamond would otherwise hand the same file over twice, and regeneration-as-diff needs a stable order). **It costs real time**: `SwiftParser` with 46 target files and 102 context files went 3.1s → 17.9s, superlinear because the resolver universe grows too. Discovery is an on-demand pass, not a build step, so the trade is accurate diagnostics and more derivations for a slower explicit run. Guarded by `ContextFileTests` (9); mutation-tested, 5 mutants, 5 killed after the walk-order one exposed that nothing pinned target-wins.

**Not fixed, and now the sharper form of the open question below:** a suite for a foreign type still cannot *name* it — the generated file imports only the scanned target. Context tells the scanner which types exist, not which module to import; the emitter would need per-type module provenance to close that.

**Four `.todo` buckets were measured and three of them were lying (2026-08-08).** A larger corpus — swift-syntax + swift-argument-parser, 24 modules, 1,368 types — was run after the nested-scanning work, and it invalidated one shipped rule and two diagnostics. **The recurring defect is a default or a first-guess message presented as knowledge**; this is the fourth, fifth and sixth instance in this file.

**(1) The `Sendable` skip rule matched a literal string, and was wrong 673 times in one module.** It looked for `Sendable` in a type's own inheritance clause and documented its blind spot — *"an inherited protocol that itself refines Sendable"* — as acceptable residue. On SwiftSyntax that blind spot is the entire library: `public protocol SyntaxProtocol: …, Sendable`, with every node declared `: SyntaxProtocol, SyntaxHashable` and never naming `Sendable`. **673 skips, all false positives; a limitation at that scale is the rule not working.** New `SendableProtocols` computes the module's `Sendable`-refining protocol set as a **fixed point** (two passes would miss a three-deep chain), and normalises `@unchecked` / `@retroactive` / generic-argument spellings. SwiftSyntax skips fell **673 → 28**, detected types rose **88 → 733**. Residual false positive, much smaller and genuinely unavoidable in a one-module syntactic scan: a protocol from *another* module that refines `Sendable`.

**(2) "No visible stored properties" described declarations nobody had read.** A whole-module scan reaches types it only ever sees *extended* — `extension Array: Foo` here, or a sibling module's type extended here. Everything member-shaped is then empty **and `TypeShape.kind` carries its `.struct` default rather than knowledge**, so the diagnostic reported a struct with an empty body — and reported *enums* as structs. Measured: **435 of the 449 in that bucket had no declaration in the target at all, 12 of them enums.** New `TypeShape.hasPrimaryDeclaration` (defaults `true`; the macro path is always attached to a declaration) gates a diagnostic that makes **no claim about the kind**, because the scanner has none. Bucket **449 → 9**, and the 9 are real memberless structs.

**(3) Every enum that failed to derive got one sentence, and for most of them its advice was impossible.** *"not `CaseIterable` and no recognized stdlib raw type … or add `: CaseIterable`"* predates Tier 4 case enumeration and survived as a catch-all over four causes — while **Swift forbids `CaseIterable` on an enum with associated values**, which is what most of them are. Split into caseless-enum / over-arity-case / unresolved-payload / cases-not-captured arms, and `todoReason` now takes the `resolve` closure so the payload arm **names the case the resolver actually could not supply** rather than the first one it sees. On the original three-package corpus all 68 members of the old bucket were payload failures and **none** were about `CaseIterable`.

**What the enum gap actually is, and why corpus choice decided the answer.** On swift-async-algorithms the 68 unresolved payloads were `UnsafeContinuation` (47), `Task` (32), `DownstreamContinuation` (11) and unbound generic parameters — *correct refusals*, since a resumption handle has no value to draw. On swift-syntax the 87 are `Syntax` (303 references), `ExprSyntax` (34), `RawTokenSyntax`, `SyntaxText` — **real inhabitable value types** that don't derive only because they are built from an arena rather than from stored properties. One root type (`Syntax`) accounts for 303 of the placeholder slots, so unblocking it would cascade. The earlier claim in conversation that "this corpus is the wrong place to look for enum yield" was right about async-algorithms and wrong as a general statement; swift.org's repos are a good corpus and finding that out cost nothing but running them.

Corpus totals after all three fixes: 35 derived generators, 25 `.todo`, and the remaining buckets are `user-defined init` (640) and `declaration not in this target` (440). The latter is not a derivation gap — those types are covered when their *own* module is scanned. **Open question, not fixed:** the plugin still emits a suite for an extension-only foreign type, and the generated file imports only the scanned target, so such a suite cannot name its type. Same class as the missing-import bug below.

**The scanner walked top-level statements only, so nested types were never declared to it — and went out under names that don't exist (2026-08-08).** A type declared inside another type, or inside an `extension` (how swift-collections writes most of its views), was never seen as a primary declaration. It entered the map solely through `extension BitSet.Counted: …`, with no stored members, no initializers and no kind, so it sat at `.todo` however derivable it was. **And `topLevelExtendedTypeName` kept only the last component**, so the suite went out as `for: Counted.self` — a name with no meaning at module scope. This is a correctness fix before a coverage one: that output could not have compiled even with a hand-written `gen()`. Measured across swift-collections + swift-numerics + swift-async-algorithms: **13 of the 23 types carrying an emitted `.todo` generator were nested, and every one was emitted unqualified.**

`accumulate` now descends into member blocks under a `namespace`, recording `BitSet.Counted` — the spelling `GeneratorResolver`'s header had already asked callers for (*"callers that scan nested types should record and reference them by qualified name"*). A conditional conformance is still skipped as a *conformance*, but its **body is now walked**: `where T: Equatable` says nothing about the types declared inside the extension.

Qualifying the key forced two follow-on changes, and skipping either would have made things worse rather than better:

- **`QualifiedTypeName.identifier`** — a scanned name is used in two incompatible positions. Type position (`for: BitSet.Counted.self`) needs the dots; identifier position (`@Suite struct …PropertyLawTests`, `@Test func hashable_…`, the `property-law-suppress:` key) cannot contain them — `@Suite struct BitSet.CountedPropertyLawTests` does not parse. One converter now serves all three identifier sites so the suite name, the test name and the suppression key can never disagree. Unqualified names pass through byte-identical, so pre-existing suppression markers still match (PRD §5.3 regeneration-as-diff).
- **`GeneratorResolver`'s leaf index** — Swift resolves `let inner: Inner` inside `Outer` through lexical scope; a flat universe keyed on `Outer.Inner` does not. Without a leaf fallback, qualifying the keys would have *cost* derivations it was meant to gain. The ambiguity rule is the same one applied to leaves: a leaf carried by two distinct shapes resolves to nothing rather than to whichever was scanned first — qualifying the keys does not make guessing safe, it only makes the guess look better informed. Top-level names outrank nested namesakes **by lookup order** (`shapesByName` is consulted first), not by pruning the index; an earlier version pruned, a mutant showed the pruning changed nothing, and the dead line is gone.

**Corpus effect, stated precisely because the earlier framing in this file overstated it.** The counts that matter are *emitted generator references*, not detected entries: `.todo` references fell **42 → 26** test methods (23 → 18 unique types) and derived references rose **10 → 17** (11 unique types). The larger "137 `.todo`" figure quoted for the `@testable import` work counted map entries, and **most of those emit no generator reference at all** — a type with no recognized stdlib conformance gets a comment stub, no suite, no `gen()` call, so its derivation strategy is never consulted. Filling those in buys nothing. The remaining real gap is `user-defined init`, `enum without CaseIterable/raw`, and `no visible stored properties`.

**The generated test file never imported the module under test (2026-08-08) — so nothing the discovery plugin emitted could compile, and four further defects were hiding behind that.** `GeneratedFileEmitter` wrote `import Testing` + `import PropertyLawKit` and nothing else, while every suite it emitted named types from the scanned target. **Measured across swift-collections + swift-numerics + swift-async-algorithms: 180 detected types, not one of them nameable.** The existing golden tests could not catch it — they assert `output.contains("import PropertyLawKit")`, and a `contains` check on a line that *is* present says nothing about one that is absent. `ModuleImportEmissionTests` pins the missing line, which is the only assertion shape that would have failed.

The import is **`@testable`**, not plain: roughly half the corpus's types are `internal` (20 public / 19 not, on unique names), and a plain import would have compiled for the public half while dropping the rest. It is also what the access model below assumes — `@testable` promotes `internal`, which is exactly where the reachability table draws its line. Verified end-to-end by generating into a real consumer package and running `swift test`: a suite compiles and runs for the first time, including for an `internal` type.

**Fixing the import made four previously-unreachable defects reachable**, all of the same shape — *the emitted code names something it cannot name* — and all now declined with a stated reason rather than emitted:

1. **Memberwise derivation ignored stored-property access.** Swift gives the synthesized memberwise init the *narrowest* member's level, so `private let secret` makes `Type(a:secret:)` uncallable — verified with `swiftc -typecheck`, and it fails **in the type's own file**, so the peer macro gets no exemption either. New `AccessLevel` + `EmissionSite` in `PropertyLawCore`; `StoredMember.accessLevel` (defaulted `.implicit`, so every existing caller is unchanged).
2. **Tier 6 ignored initializer access.** `public struct { private init(a:b:) }` derived a call it could not make. This is the field `takesPrivateStorage` said it wanted (*"`InitializerSignature` does not carry it"*) — it does not replace that rule, which catches a *public* `init(_bits:count:)` whose parameters constrain each other. The guard lives in `isDeclined`, which `continue`s, so a type with one restricted and one reachable initializer still derives through the reachable one.
3. **`private` / `fileprivate` types got suites that could not name them.** `@testable` promotes `internal`, not these. Dropped and reported via `SkippedType`.
4. **`public` types without `Sendable` got suites that could not type-check.** Swift infers `Sendable` for non-public types only, and every `check…PropertyLaws` entry point is constrained `Value: … & Sendable`. **This one was invisible in principle until the import landed** — while the file named no types at all, nothing reached the point of being rejected for it. Verified with a two-target package that `package` types *are* implicitly Sendable, so the rule stops at `public` / `open`. 35 of the corpus's 180 hit this.

**`private(set)` is deliberately not treated as a restriction**, and the distinction is load-bearing: it restricts the setter, the initializer follows the getter, and the cross-file call compiles. `MemberBlockInspector.accessLevel(of:)` enforces it by skipping detail-carrying modifiers, and is shared by the stored-property, initializer, and type-declaration readers so all three obey one rule. **`fileprivate` is site-dependent, which is why `EmissionSite` exists rather than a bool**: a peer-macro expansion is attributed to the decoratee's file and *can* reach it, so declining it unconditionally would have regressed code that compiles today. `PropertyLawSuiteMacro` passes `.sameFile`; everything else takes the conservative `.separateFile` default. `EndToEndTests` compiles a `fileprivate`-member type through the macro as the proof — a string-comparison expansion test could not tell the difference.

**Seeded finite path for the NaN generators (2026-07-26).** `Gen<Double>.doubleWithNaN()` and `Gen<Float>.floatWithNaN()` drew their finite values from `Double.random(in:)` / `Float.random(in:)` — the **system** RNG, invisible to a seed. The NaN *positions* replayed (the tag was seeded); the values did not, so a FloatingPoint law failing on an ordinary value could not be reproduced from the seed it failed under — precisely the case where the exact input matters. Both now thread the engine's seeded `Gen<Double>.double(in:)` / `Gen<Float>.float(in:)` via `zip`, which also gains `Shrink.Floating` on the value. **Nothing caught this**: both generators are used by `FloatingPointLawsTests` and `SameResultTests` on every run, and a law that holds does not care whether its inputs are reproducible. Found by pointing SwiftProjectLint's `Non-Injected Nondeterminism` rule at this repo (`SwiftInferProperties/docs/measurements/roadtest-self-dogfood.md` §14); confirmed by drawing the same seed twice. Guarded by `NaNGeneratorSeedingTests` (6) — replay, NaN-position stability, **finite values actually vary** (a constant would satisfy every replay assertion and destroy the generator), the ~1-in-20 rate, and different-seeds-differ. Mutation-tested, 3 mutants killed, including a revert to `Double.random`. **`PropertyLawComplex.edgeCaseBiased()` deliberately keeps its unseeded finite path** and now says so at the call site: there the 12 curated edge cases are the payload and the filler only sets the 90/10 ratio, with `determinismOnSeededTagDecisions` pinning the guarantee it actually offers. Revisit if a law is ever found failing on that finite path.

**Two `PropertyLawCore` codegen fixes (2026-07-26), both found by SwiftInferProperties' self-dogfood road test — see `SwiftInferProperties/docs/measurements/roadtest-self-dogfood.md` §9.2.**

**(1) `.caseIterable` emitted an expression that could never compile.** `GeneratorExpressionEmitter` rendered `Gen<T>.element(of: T.allCases)`, but `Gen.element(of:)` is declared `where Value == C.Element?` — so that spelling asks the compiler to prove `T == T?` and fails with *"requires the types 'T' and 'T?' be equivalent."* Now `Gen<T?>.element(of: T.allCases).compactMap { $0 }`, matching the spelling every **hand-written** call site in this repo already used (`CaseIterableLawsTests`, `RawRepresentableLawsTests`, the planted-bug suites). Explicit `Gen<T?>` rather than inferred, because the expression is interpolated into *composed* positions (one member of a `zip(…).map { … }`) where inference is fragile. **Blast radius was wider than one consumer:** the `@PropertyLawSuite` macro and the `propertylawcheck discover` plugin both emit this arm, so every `CaseIterable` enum they touched got uncompilable test code — and three golden tests (`MacroExpansionMultiTypeTests`, `DiagnosticsTests`, `EmitterGoldenTests`) plus the emitter's own unit test pinned the broken string verbatim. A codegen test that compares text to text can have both sides wrong together, and here four of them did.

Required a test-only `PropertyBased` dep on `PropertyLawCoreTests` (`PropertyLawCore` itself stays a dependency-free leaf). **Add a case here whenever you add a `DerivationStrategy` arm.**

**(2) `GeneratorResolver` silently resolved an ambiguous type name to an arbitrary shape.** `TypeShape.name` is one unqualified string, so a scanner recording nested types under bare names hands the resolver several distinct shapes all called `Kind`. The universe was built with `uniquingKeysWith: { first, _ in first }` — whichever arrived first won, and a member typed `Kind` could be generated from an unrelated type's nested enum, with no diagnostic anywhere. In the road-test subject **eight** distinct `Kind`s collapsed to one, and the survivor was a CLI-internal enum unrelated to every member referencing it. New public `ambiguousTypeNames` lets a scanner report the collisions. **Qualified names are the escape hatch and need no emitter support** — every emitter interpolates `typeName` verbatim, so `Foo.Kind` already comes out right; callers that scan nested types should record them qualified. Guarded by five tests in `GeneratorResolverTests` (refusal, reporting, owner-stays-`.todo`, identical-duplicate is *not* ambiguity, qualified-name round trip).

Both harnesses require `Invariant: Sendable` so the `Invariant.Type` metatype crosses the actor-isolation boundary cleanly (PerLawDriver runs on the configured backend's actor). Reducer is `@Sendable` for the same reason. Uses the existing internal `LawCheck` / `PerLawDriver.run` / `PropertyLawViolation.throwIfViolations` infrastructure that the algebraic checks use. 6 tests in `Tests/PropertyLawKitTests/InteractionInvariantLawsTests.swift` covering both harnesses' positive control (invariant always holds), negative control (faulty reducer surfaces violation), initial-state violation, and the empty-set degenerate case. **Still deferred to a future minor:** PropertyLawMacro discovery integration (so conforming types emit a property test on every CI run automatically) — that's a SwiftSyntax-based code-gen layer rather than a runtime harness, and the harness functions can be wired manually in test files in the interim.

**v2.3.0 `InteractionInvariant` protocol family.** Type-level scaffolding for SwiftInferProperties v2.0 M9 (InteractionInvariantBridge — PRD §9). Six new public protocols in `PropertyLawKit/Public/InteractionInvariant.swift`: root `InteractionInvariant` (carries `associatedtype State` + `static func invariantHolds(in state: State) -> Bool`), plus four state-predicate refinements with **no added requirements** (mutually independent per PRD §9.4 — no hierarchy): `CardinalityInvariant`, `ReferentialIntegrityInvariant`, `BiconditionalInvariant`, `ConservationInvariant`. The fifth, `ActionIdempotenceInvariant`, refines the root but adds a separate law shape — `associatedtype Action: Hashable` + `static var idempotentActions: Set<Action> { get }` — because its property ("applying a from idempotentActions twice equals once") is action-applicative, not a state-level predicate. The inherited `invariantHolds(in:)` defaults to `true` on `ActionIdempotenceInvariant` so conformers don't have to provide a trivial implementation. 7 tests in `Tests/PropertyLawKitTests/InteractionInvariantTests.swift`. **Deferred to a future minor:** the `checkInteractionInvariantPropertyLaws` harness function (currently the property check is done by SwiftInferProperties' M3.E verify-interaction subcommand) and PropertyLawMacro discovery integration (so conforming types emit a property test on every CI run). Both are layered concerns that don't block M9's Bridge writeout — the protocols are the load-bearing scaffolding that lets the user-side conformance stub compile.

## What this repo is

A design / proposal repository for two related Swift packages:

- **SwiftPropertyLaws** — `PropertyLawKit` (a runtime library of property-based protocol law checks for Swift Standard Library protocols: `Equatable`, `Hashable`, `Comparable`, `Codable`, `Collection`, `SetAlgebra`) plus `PropertyLawMacro` (a SwiftSyntax-based layer that detects conformances and generates `checkXxxPropertyLaws(...)` test stubs). See `docs/Protocols/SwiftPropertyLaws PRD.md`.
- **SwiftInferProperties** — downstream of SwiftPropertyLaws. `TemplateEngine` (signature-pattern matcher that proposes round-trip / idempotence / commutativity / etc. tests) and `TestLifter` (lifts existing XCTest / Swift Testing methods into generalized property tests). See `docs/SwiftInferProperties PRD.md`.

The intended dependency direction is one-way: `SwiftInferProperties → SwiftPropertyLaws (PropertyBackend) → swift-property-based`. v1 ships `swift-property-based` as the single backend; see the "Single-backend by design" note above.

## Design decisions baked into v0.2

A future Claude implementing the package should follow these decisions rather than re-litigate them. They live in the PRD; this is a quick map.

- **Strictness tiers per protocol law.** Strict / Conventional / Heuristic. Conventional and Heuristic violations do not fail tests by default — only when the caller passes `.strict`. PRD §4.2.
- **Generator derivation is opt-in and visible.** `using:` requires an explicit `Gen<T>` by default; `.derived` walks a priority list (CaseIterable → memberwise-Arbitrary → RawRepresentable → Codable round-trip), and the *only* fallback when nothing matches is a non-compiling `.todo` stub. Silent green tests from weak generators are the failure mode being prevented. PRD §5.7.
- **Layered PropertyLawMacro scope.** Core = conformance → test stubs (always on). Advisory = missing-conformance suggestions, cross-function discovery (off by default). Experimental = pattern warnings, Codable-derived generators (off by default). Don't put new features in Core without justification. PRD §5.2.
- **Discovery is a Swift Package Plugin, not a macro.** The per-suite trait/macro is a macro; whole-module discovery is a build-tool plugin because macros can't read sibling files. PRD §9 Decision 4.
- **`@PropertyLawSuite` is a Swift Testing custom Trait** (`@Test(.propertyLaws(...))`). Reuse the runner's reporting / filtering / parallelization rather than reinventing them. The freestanding `@PropertyLawSuite` macro form remains for non-Swift-Testing callers. PRD §9 Decision 5.
- **`PropertyBackend` is public as of M4, single-backend by design.** Closure-shaped abstraction (`sample: (inout Xoshiro) -> Input`, `property: @Sendable (Input) async throws -> Bool`) per the M4 backend-survey seam recommendation. `SwiftPropertyBasedBackend` is the only backend v1 ships; the abstraction stays so future alternatives drop in without protocol changes.
- **Pattern warnings, not contradiction detection.** §5.6 is a curated, named-pattern list (idempotent+involutive ⇒ identity, etc.). It does not aspire to soundness/completeness; new patterns require maintainer commits, not graph reasoning. PRD §5.6.
- **Trial budget is part of the API.** `.sanity` (100) / `.standard` (1,000, default) / `.exhaustive` (10,000) / `.custom`. CI cost is a real constraint. PRD §4.4.
- **Suppression is first-class.** Per-type, per-law, intentional-violation, and custom-equivalence APIs exist (PRD §4.7). This is the adoption-failure escape hatch.
- **Validation gate before 1.0.** Must catch a real semantic bug in 5+ popular open-source Swift packages. PRD §8. Don't ship 1.0 without that.
- **Framework self-test gate (every CI run).** Planted-bug suite asserts the framework catches every Strict violation; PropertyLawKit eats its own dog food. PRD §8.
- **Inheritance is implicit by default.** `checkHashablePropertyLaws` runs Equatable's laws automatically; `checkComparable` runs Equatable's; `checkCollection` runs Sequence's and IteratorProtocol's. Property tests are too slow to make "remember to chain inherited suites" the caller's responsibility — forgetting is a silent way to miss real bugs. Opt-out via `laws: .ownOnly`. The Discovery plugin emits the most-specific call per type (one `checkComparable`, not separate `checkEquatable` + `checkComparable`) so generated tests don't double-run inherited laws. PRD §4.3.
- **Coverage scope is tiered, not exhaustive.** v1 = the 8 protocols in §4.3 (incl. `Sequence`/`IteratorProtocol`). v1.1 candidates and permanently-out-of-scope protocols are enumerated in §4.3 Coverage Scope, cross-referenced to `docs/Protocols/Swift Standard Library Protocols.md`. Don't quietly add new protocols to Core; add them to Coverage Scope first.
- **Generic conformances need explicit bindings.** `@LawGenerator(bindings: [Container<Int>.self, Container<String>.self])` — the plugin does not enumerate the unbounded generic instantiation space. PRD §4.4 Generic Conformances.
- **`Codable.partial(fields:)` uses `PartialKeyPath`, not strings.** Type-safe, refactor-safe. PRD §4.3.
- **Replay seeds carry an environment fingerprint.** Swift version + backend version + generator-schema hash. A stale seed fails loudly instead of silently replaying as a different test. PRD §4.6.
- **Near-miss is defined per-protocol.** Don't invent a global definition; consult the §4.6 near-miss table. Backends that can't track near-misses report `nearMisses: nil`, not `[]`.
- **Generator registry is an actor.** Concurrency-safe under Swift 6 strict concurrency; not `static var`. PRD §4.5 Actor-Isolated Types.
