# PropertyLawKit v2.6 — Backend Shrinking (minimal counterexamples)

Drafted 2026-06-26 against repo state at commit `HEAD` (post-v2.5, ships in v2.6.0
alongside the Ring protocol cluster + three refactors).
**Implemented 2026-06-26 (v2.6.A): unary, binary + ternary shrinking, driver-level.**

## Why this milestone

`SwiftPropertyBasedBackend` has carried the note *"Shrinking is not yet exercised
(M5+ scope); this backend reports the first failing input verbatim"* since M1. M5
shipped — but as the **confidence-reporting** upgrade (replay-environment validation,
near-miss tracking, opt-in `CoverageClassifier`). Shrinking was the part of "M5+"
that never landed. This is its own engine milestone: **v2.6**.

The motivation is the cross-repo loop. SwiftInferProperties is opening a
*minimal-counterexample & replay-corpus* epic (`SwiftInferProperties/docs/v1.141
Calibration Plan.md`): its `verify` pipeline already runs inferred properties and
moves the tier (`Tier.verified`), but it reports the **first** failing input, not the
**minimal** one — and a random 17-digit `Double` is far less useful to a developer
than `0.0`. A second consumer is incoming: `SwiftIdempotencyPropertyBased`
(`swiftIdempotency/docs/property-based-assertions-design.md`). Both need the kit to
minimize. Putting shrinking in the kit serves both — and every direct PropertyLawKit
user — from one place.

## Implemented (v2.6.A) — driver-level, not backend-level

The original sketch (preserved below under "Alternative considered") put shrinking
*in the backend* and extended `BackendCheckResult` / `CheckResult.Outcome`. Reading
the code showed a strictly cleaner path:

- **`BackendCheckResult.failed` is matched by a cross-repo custom-backend conformer**
  (`SwiftInferProperties/.../EmittedIdempotenceLawSoundnessTests.swift`) and the
  in-repo `DownstreamPropertyBackendSmokeTests`. `Outcome.failed(counterexample:)` has
  seven construction/match sites. Changing either enum's arity breaks both repos.
- `PerLawDriver` already *"owns the policy bits the backend itself doesn't
  (suppression rewriting, CheckResult assembly, environment fingerprinting, near-miss
  snapshot, coverage accumulation)."* Shrinking is exactly such a policy.

So shrinking landed as a **`PerLawDriver` policy** that re-runs the law's own
`property` as the failure oracle. **`PropertyBackend`, `BackendCheckResult`, and
`SwiftPropertyBasedBackend` are untouched** — zero public-API change, zero cross-repo
break (better than the sketch's "call-site compatible").

### What actually changed — four files

1. **`Model/CheckResult.swift`** — two additive fields, mirroring the existing
   `nearMisses` / `coverageHints` optional-metadata precedent. `Outcome` is untouched
   (no switch ripple anywhere):
   ```swift
   public let shrunkFrom: String?   // pre-shrink counterexample; nil when shrinkSteps == 0
   public let shrinkSteps: Int      // 0 when no shrinker / already minimal
   ```
   `outcome`'s `counterexample` always holds the **minimal** form; `shrunkFrom` holds
   the original first-failing form.

2. **`Internal/PerLawDriver.swift`** —
   - `LawCheck<Input>` gains `let shrink: (@Sendable (Input) -> [Input])?` (explicit
     init, default `nil`, so all existing `LawCheck(...)` sites compile unchanged).
   - `packageResult` is `async`, takes the whole `LawCheck` (keeps it ≤ 5 params), and
     in the `.failed` branch runs `minimize` when a shrinker is present.
   - `minimize` is greedy descent returning a `Minimized<Input>` struct
     `{ input, steps, error }` (a struct, not a 3-tuple — `large_tuple`-clean):
     from the failing input, take the first shrink candidate that *still* fails
     (`property` false or throws), restart the walk from it, to fixpoint or a 1000-step
     cap.

3. **`Internal/LawCheckBuilders.swift`** — `runUnaryLaw` / `runBinaryLaw` /
   `runTernaryLaw` gain an optional per-element `shrink: (@Sendable (Value) -> [Value])?
   = nil`. The binary form lifts it into a pair shrinker (shrink position 0 holding 1,
   then position 1); the ternary form lifts it via a `liftToTripleShrinker` helper
   (one position at a time). That helper is the kit's only `large_tuple` site — a
   3-value law's input is intrinsically a triple, so the shrinker type must name
   `(Value, Value, Value)` — and the rule is waived with a **scoped
   `swiftlint:disable/enable large_tuple` around that one helper**, not by relaxing
   the project config.

4. **`Public/EquatableLaws.swift`** (proving family) — `checkEquatablePropertyLaws`
   gains `shrink: (@Sendable (Value) -> [Value])? = nil`, threaded to reflexivity
   (unary), symmetry + negationConsistency (binary), and transitivity (ternary).
   Source-compatible: existing callers (incl. SwiftInfer-generated stubs) omit the
   new defaulted argument.

A law helper enables shrinking by passing a per-element shrinker, e.g. from
swift-property-based's `FixedWidthInteger.shrink(towards:)`:
```swift
try await checkEquatablePropertyLaws(
    for: MyType.self, using: gen,
    shrink: { $0.raw.shrink(towards: 0).map(MyType.init) })
```

### Design principle — preserve the closure seam

`PropertyBackend` is public-as-of-M4 and single-backend by design; its doc-comment
records that the seam is *closure-level* specifically so the protocol stays
"non-leaky against any backend's generator/shrinking representation." Driver-level
shrinking honors this perfectly: the shrinker is a value-level
`(@Sendable (Input) -> [Input])` closure — the kit never threads a `Generator`. The
per-element shrinkers come from swift-property-based's `Shrink` namespace
(`FixedWidthInteger.shrink(towards:)`, etc.), which is value → values.

## Correctness

- **R3 (float tolerance) — by construction.** A candidate is accepted only if it
  *also* fails the real `property`, which carries the law's exact comparison
  (`isApproximatelyEqual`). A "minimal" value that doesn't fail can never be reported.
- **Determinism / replay.** Shrinking is a pure function of `(failingInput, shrink,
  property)`. `initialSeed` reproduces `failingInput`; `minimize` reproduces the
  minimal. A stored seed alone reproduces both — what SwiftInfer's v1.143 replay
  corpus relies on. (Verified: `shrinkingIsDeterministicUnderAFixedSeed`.)
- **Termination.** `Shrink.Integer` strictly converges via `midpoint` (log steps);
  pair shrinking is finite per step; `cap` (1000) is a backstop.
- **Throw fidelity.** `minimize` tracks the error of the last still-failing candidate,
  so a shrunk throwing failure reports the shrunk throw.

## Rollout — per-law opt-in

Equatable is wired in v2.6.A. Remaining scalar/tuple families (Comparable,
AdditiveArithmetic, Numeric, SignedNumeric, the integer cluster, …) opt in the same
way: add a defaulted `shrink:` to the public function, thread it to the unary/binary
builders. Laws that pass no shrinker degrade to `shrinkSteps: 0` and pre-v2.6
first-failure behavior — no regression, no error.

## Tests

`Tests/PropertyLawKitTests/BackendShrinkingTests.swift` (5 tests, all passing; total
486 → 491):

- `shrinkingReducesToASmallerStillFailingInput` — minimal still fails and ≤ original.
- `noShrinkerReportsFirstFailingInputVerbatim` — `shrinkSteps == 0`, identical to
  pre-v2.6.
- `shrinkingIsDeterministicUnderAFixedSeed` — replaying `result.seed` reproduces the
  same minimal counterexample + step count.
- `ternaryLawShrinksEachComponentTowardZero` — a triple sum-threshold law shrinks each
  component; the minimal triple still fails.
- `equatableSuiteThreadsAShrinkerEndToEnd` — a planted non-reflexive Equatable shrinks
  to exactly the threshold (`raw: 1000`) through the public suite.

## Deferred

- **Remaining 21 families** — per-law opt-in rollout above. (Unary, binary, and
  ternary shapes are all supported by the builders; each family just needs its public
  function to thread a `shrink:`.)
- **Aggregate-mode laws** (`AggregateDriver`) bypass the per-trial path by design.
- **`ViolationFormatter` shrink trace** beyond `shrunkFrom` — presentation, can follow.

## Alternative considered (not taken) — backend-level shrinking

The original sketch added `shrink:` to `PropertyBackend.check` (with a forwarding
extension overload) and extended `BackendCheckResult.failed` /
`CheckResult.Outcome.failed` with `shrunkInput` / `shrinkSteps`, running the greedy
loop inside `SwiftPropertyBasedBackend`. Rejected because changing those public enum
arities breaks the in-repo smoke test **and** SwiftInferProperties' custom-backend
test, for no benefit over the driver-level approach — the driver already has the
`property` closure and owns result assembly. Recorded here so the seam decision is
traceable.
