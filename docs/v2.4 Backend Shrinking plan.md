# PropertyLawKit v2.4 — Backend Shrinking (minimal counterexamples)

Drafted 2026-06-26 against repo state at commit `HEAD` (post-v2.3).

## Why this milestone

`SwiftPropertyBasedBackend` has carried the note *"Shrinking is not yet exercised
(M5+ scope); this backend reports the first failing input verbatim"* since M1. M5
shipped — but as the **confidence-reporting** upgrade (replay-environment validation,
near-miss tracking, opt-in `CoverageClassifier`). Shrinking was the part of "M5+"
that never landed. This is its own engine milestone: **v2.4**.

The motivation is the cross-repo loop. SwiftInferProperties is opening a
*minimal-counterexample & replay-corpus* epic (`SwiftInferProperties/docs/v1.141
Calibration Plan.md`): its `verify` pipeline already runs inferred properties and
moves the tier (`Tier.verified`), but it reports the **first** failing input, not the
**minimal** one — and a random 17-digit `Double` is far less useful to a developer
than `0.0`. A second consumer is incoming: `SwiftIdempotencyPropertyBased`
(`swiftIdempotency/docs/property-based-assertions-design.md`). Both need the kit to
minimize. Putting shrinking in the backend serves both — and every direct
PropertyLawKit user — from one place.

## Design principle — preserve the closure seam

`PropertyBackend` is public-as-of-M4 and **single-backend by design**. Its
doc-comment records the M4 backend-survey decision: the seam is *closure-level*
(`sample: (inout Xoshiro) -> Input`, `property: @Sendable (Input) async throws -> Bool`)
specifically so the protocol stays "non-leaky against any reasonable property-based
backend's generator/shrinking representation."

Shrinking honors that seam. swift-property-based's `Shrink` namespace is **value →
values**, generator-independent:

- `FixedWidthInteger.shrink(towards:) -> Shrink.Integer<Self>` — halves via `midpoint`
- `Shrink.shrinkTuple(_:shrinkers:) -> Shrink.Tuple` — shrinks one tuple element at a time (fits law inputs `(T, T)` / `(T, T, T)` exactly)
- `Shrink.None<Element>` — empty sequence for non-shrinkable types
- plus `Shrink+Float`, `Shrink+Collection`, `Shrink+Optional`

So shrinking enters as a value-level closure `shrink: (@Sendable (Input) -> [Input])?`.
The protocol never sees `Generator` or `ShrinkSequence` — it sees `Input` values in,
`[Input]` candidates out. This is *more* in keeping with the seam than threading the
generator would be.

## Scope — four files

### 1. `Public/PropertyBackend.swift`

`shrink:` becomes a requirement (dynamic dispatch through `any PropertyBackend`
requires it). The old 4-arg shape becomes a **forwarding extension overload**, so
existing call sites compile unchanged:

```swift
public protocol PropertyBackend: Sendable {
    var identifier: String { get }
    func check<Input: Sendable>(
        trials: Int, seed: Seed?,
        sample: @Sendable (inout Xoshiro) -> Input,
        shrink: (@Sendable (Input) -> [Input])?,           // NEW; nil = no shrinking
        property: @Sendable (Input) async throws -> Bool
    ) async -> BackendCheckResult<Input>
}

extension PropertyBackend {
    public func check<Input: Sendable>(                     // back-compat: 4-arg callers
        trials: Int, seed: Seed?,
        sample: @Sendable (inout Xoshiro) -> Input,
        property: @Sendable (Input) async throws -> Bool
    ) async -> BackendCheckResult<Input> {
        await check(trials: trials, seed: seed, sample: sample, shrink: nil, property: property)
    }
}

public enum BackendCheckResult<Input: Sendable>: Sendable {
    case passed(trialsRun: Int, initialSeed: Seed)
    case failed(trialsRun: Int, initialSeed: Seed,
                failingInput: Input,     // first failure = replay anchor
                shrunkInput: Input,      // minimal; == failingInput when shrinkSteps == 0
                shrinkSteps: Int,
                thrownError: ErrorBox?)
}
```

### 2. `Internal/Backends/SwiftPropertyBasedBackend.swift`

Greedy descent, reusing the law's own `property` as the failure oracle:

```swift
public func check<Input: Sendable>(
    trials: Int, seed: Seed?,
    sample: @Sendable (inout Xoshiro) -> Input,
    shrink: (@Sendable (Input) -> [Input])?,
    property: @Sendable (Input) async throws -> Bool
) async -> BackendCheckResult<Input> {
    var rng = seed?.makeXoshiro() ?? Xoshiro()
    let initialSeed = Seed(xoshiro: rng)
    var ran = 0
    for _ in 0..<trials {
        ran += 1
        let input = sample(&rng)
        let (fails, err) = await Self.evaluate(property, input)
        if fails {
            let (minimal, steps, lastErr) =
                await Self.minimize(input, firstError: err, shrink: shrink, property: property)
            return .failed(trialsRun: ran, initialSeed: initialSeed,
                           failingInput: input, shrunkInput: minimal,
                           shrinkSteps: steps, thrownError: lastErr)
        }
    }
    return .passed(trialsRun: ran, initialSeed: initialSeed)
}

private static func evaluate<I>(_ p: @Sendable (I) async throws -> Bool, _ x: I) async -> (Bool, ErrorBox?) {
    do { return (try await p(x) == false, nil) } catch { return (true, ErrorBox(error)) }
}

private static func minimize<I>(_ start: I, firstError: ErrorBox?,
    shrink: (@Sendable (I) -> [I])?, property: @Sendable (I) async throws -> Bool
) async -> (I, Int, ErrorBox?) {
    guard let shrink else { return (start, 0, firstError) }
    var current = start, lastError = firstError, steps = 0
    let cap = 1000
    outer: while steps < cap {
        for candidate in shrink(current) {
            let (fails, err) = await evaluate(property, candidate)
            if fails { current = candidate; lastError = err; steps += 1; continue outer }
        }
        break   // fixpoint: nothing smaller still fails
    }
    return (current, steps, lastError)
}
```

### 3. `Model/CheckResult.swift`

Extend `.failed` only; update the `counterexample` computed var:

```swift
case failed(counterexample: String, shrunkFrom: String?, shrinkSteps: Int)
```

`shrunkFrom == nil` ⇔ no shrinking happened. Hashable stays synthesized.

### 4. `Internal/PerLawDriver.swift`

`LawCheck<Input>` carries an optional shrinker (explicit init with `shrink: … = nil`
so the dozens of existing law helpers compile untouched); `packageResult` formats
both ends through the existing `formatCounterexample`:

```swift
let minimal  = formatCounterexample(shrunkInput, thrownError)
let original = shrinkSteps > 0 ? formatCounterexample(failingInput, thrownError) : nil
outcome = .failed(counterexample: minimal, shrunkFrom: original, shrinkSteps: shrinkSteps)
```

A law helper enabling shrinking supplies, e.g. for an `(Int, Int)` law:

```swift
shrink: { (pair: (Int, Int)) in
    Array(Shrink.shrinkTuple(pair,
        shrinkers: { $0.shrink(towards: 0) }, { $0.shrink(towards: 0) }))
}
```

## Correctness

- **R3 (float tolerance) — by construction.** A candidate is accepted only if it
  *also* fails the real `property`, which carries the law's exact comparison
  (`isApproximatelyEqual`). We can never report a "minimal" value that doesn't fail.
- **Determinism / replay.** Shrinking is a pure function of `(failingInput, shrink,
  property)`. `initialSeed` reproduces `failingInput`; `minimize` reproduces
  `shrunkInput`. A stored seed alone reproduces both — which is what
  SwiftInferProperties' v1.143 replay corpus relies on.
- **Termination.** `Shrink.Integer` strictly converges via `midpoint` (log steps);
  tuple shrinking is one element at a time over finite per-step candidate sets; `cap`
  is a backstop.
- **Throw fidelity.** `lastError` tracks the error of the last still-failing
  candidate, so a shrunk throwing failure reports the shrunk throw, not the original.

## Rollout — per-law opt-in

Enable shrinking law-by-law, scalar/tuple laws first (Equatable, Comparable,
AdditiveArithmetic, Numeric, SignedNumeric, the integer cluster). Laws that pass no
shrinker (or carriers with no `Shrink.*`) degrade gracefully to `shrinkSteps: 0` and
today's first-failure behavior — no regression, no error.

## Compatibility

**Call-site compatible.** Only `SwiftPropertyBasedBackend` (the single conformer) and
the kit-internal `.failed` switches (`PerLawDriver.packageResult`, the
`CheckResult.counterexample` accessor) change. External 4-arg `check` callers route
through the forwarding extension. The `CheckResult.Outcome.failed` associated-value
change is the one source-visible delta — additive (new fields), but exhaustive
switches over `Outcome` in downstream code recompile. Version as a minor (v2.4.0)
with a release note flagging the `Outcome.failed` shape.

## Tests

`Tests/PropertyLawKitTests/BackendShrinkingTests.swift` (Swift Testing), mirroring
the `EffectSymbolTableLaws` fixpoint style via planted-bug laws with known minima:

- shrink output still fails the property;
- shrink output ≤ input in the shrink order;
- shrinking terminates (cap never hit on convergent shrinkers);
- re-shrinking a minimal value is a fixpoint (`shrinkSteps == 0`);
- non-shrinkable carrier (`Shrink.None`) → identical to pre-v2.4 behavior;
- throwing-law shrink reports a throw, with the shrunk error.

## Deferred

- Structural shrinkers for arbitrary user types beyond `Shrink.shrinkTuple` +
  per-component `Shrink.*` (e.g. recursive enums) — SwiftInferProperties'
  `DerivationStrategist` owns generator/shrinker synthesis for carriers; the kit
  ships the loop + the stdlib component shrinkers.
- Wiring shrinking into the aggregate-mode laws (`AggregateDriver`) — those bypass the
  per-trial backend by design; out of scope.
- Surfacing the shrink trace in the `ViolationFormatter` output beyond `shrunkFrom` —
  presentation, can follow.
