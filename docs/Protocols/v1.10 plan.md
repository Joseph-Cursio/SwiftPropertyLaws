# PropertyLawKit v1.10 — Kit-Defined Algebraic Protocols (Ring)

Drafted 2026-06-07 against repo state at commit `HEAD` (post-v1.9).

## Why this cluster

The v1.8 plan named `Ring` explicitly as deferred work: *"Group needs an `inverse` requirement; Semilattice adds idempotence; Ring is two interacting structures (additive abelian group + multiplicative semigroup with distributivity). Claim-only stays for these. Land when SwiftInferProperties M8 motivates them. Probably a v1.10 cluster."* v1.9 shipped Group + Semilattice. v1.10 closes the cluster with Ring.

The motivation is the same cross-repo loop that drove v1.8/v1.9, and it is currently **broken for ring-shaped types**. SwiftInferProperties already *infers* ring structure — its CLAUDE.md lists "semigroup / monoid / group / semilattice / **ring**" as inferred algebraic structures, and the v2.0 PRD's RefactorBridge suggests conformance to kit-defined protocols when ≥3 strong signals accumulate. But there is no kit-defined `Ring` to conform to, so a ring claim has nowhere to land: SwiftInferProperties can detect the shape, but the discovery plugin can't emit a law-check and CI can't enforce it. v1.10 supplies the missing protocol so the inference → conformance → verification loop closes for the last algebraic structure SwiftInferProperties already speaks.

This is the kit's first **two-operation** protocol. Every prior algebraic protocol (Semigroup through Semilattice) is built on a single `combine(_:_:)` plus an optional `identity` / `inverse`. Ring is the kit's first structure where two operations interact through distributivity — which forces a design decision the single-op cluster never had to make (see §"Why standalone").

## Scope

One protocol, eleven Strict laws — the kit's largest single-protocol law set after `BinaryInteger` (16) and `FloatingPoint` (14), reflecting that a ring axiomatizes two interacting structures at once.

| Protocol | Requirements | Own laws | Inherited |
|---|---|---|---|
| `Ring` | `static var zero`, `static var one`, `static func add(_:_:)`, `static func multiply(_:_:)`, `static func negate(_:)` | 11 (see below) | (none — standalone, see §"Why standalone") |

Ring requires `Equatable` to *check* the laws (same posture as every kit-defined protocol since Semigroup) but not to *declare* the conformance.

### The eleven laws

**Additive abelian group** (the `(add, zero, negate)` structure):

| Law | Statement | Samples |
|---|---|---|
| `addAssociativity` | `add(add(a, b), c) == add(a, add(b, c))` | 3 |
| `addCommutativity` | `add(a, b) == add(b, a)` | 2 |
| `addLeftIdentity` | `add(.zero, a) == a` | 1 |
| `addRightIdentity` | `add(a, .zero) == a` | 1 |
| `addLeftInverse` | `add(negate(a), a) == .zero` | 1 |
| `addRightInverse` | `add(a, negate(a)) == .zero` | 1 |

**Multiplicative monoid** (the `(multiply, one)` structure — a *ring with unity*, see §"Why with unity"):

| Law | Statement | Samples |
|---|---|---|
| `multiplyAssociativity` | `multiply(multiply(a, b), c) == multiply(a, multiply(b, c))` | 3 |
| `multiplyLeftIdentity` | `multiply(.one, a) == a` | 1 |
| `multiplyRightIdentity` | `multiply(a, .one) == a` | 1 |

**Distributivity** (the cross-structure laws — the reason Ring exists as a distinct protocol rather than two independent conformances):

| Law | Statement | Samples |
|---|---|---|
| `leftDistributivity` | `multiply(a, add(b, c)) == add(multiply(a, b), multiply(a, c))` | 3 |
| `rightDistributivity` | `multiply(add(a, b), c) == add(multiply(a, c), multiply(b, c))` | 3 |

All eleven are **Strict** (a violation fails the suite). Distributivity is checked both-sided because the kit does not assume commutative multiplication — a non-commutative ring (e.g. square matrices) satisfies left- and right-distributivity independently, and a buggy `multiply` can break one while preserving the other.

## Design decisions

### Why standalone (Ring refines nothing in the existing DAG)

Every kit-defined algebraic protocol so far forms a single refinement chain `Semigroup → Monoid → CommutativeMonoid → {Group, Semilattice}`, unified by a single `combine(_:_:)` operation. A ring's *additive* structure is an abelian group and its *multiplicative* structure is a monoid — so the tempting move is to make `Ring: CommutativeMonoid` (or `: Group`) and reuse `combine` for `add`.

That move is wrong, for a concrete reason: **`combine` can only name one operation.** If `Ring` inherited the chain with `combine = add`, then `multiply` would be a second-class citizen with no inherited laws, and worse, a type could not simultaneously declare `: Group` (with `combine` meaning something else) and `: Ring`. Binding `combine` to `add` leaks the additive operation into the type's identity in a way that collides with any other single-op conformance.

So `Ring` is **standalone**: it declares its own `add` / `multiply` / `zero` / `one` / `negate` and `subsumedProtocols` returns `[]`. Nothing subsumes Ring and Ring subsumes nothing. A type that is both `Ring` and (say) `Monoid` via a different operation surfaces both checks — which is correct, because they are genuinely different claims. This mirrors the v1.9 decision to leave `Group` and `CommutativeMonoid` as incomparable arms (KnownProtocol `subsumedProtocols` comment; SwiftInferProperties M8 open decision #6).

The cost is that Ring re-implements additive associativity / commutativity / identity / inverse rather than inheriting them from Group. That duplication is the honest price of two named operations, and it keeps every other protocol's `combine` contract clean. The v1.8 plan anticipated exactly this — it grouped Ring with the structures that "need [cross-structure compatibility laws] more."

### Why with unity (`one` is required, not optional)

A *rng* (ring without unity) drops the multiplicative identity. The kit requires `one` and tests `multiplyLeftIdentity` / `multiplyRightIdentity` because:

- Stdlib's `Numeric` (which the kit already covers) has a multiplicative identity; the kit-defined Ring should match that baseline so a "promote my `Numeric`-shaped type to Ring" suggestion is law-compatible.
- Every common Swift ring carrier the inference engine will surface — `Int`-modular (`Z/nZ`), matrices, polynomials, dual numbers, Gaussian integers, boolean rings — has a natural `one`. Rngs are rare enough in idiomatic Swift that requiring `one` costs almost nothing and buys two extra laws.
- A future `Rng` protocol (multiply as `Semigroup`, no `one`) can be added if a real carrier demands it; making `Ring` the with-unity default is the higher-value starting point.

### Why `add` / `multiply` (not `+` / `*` operators)

Same rationale as `combine(_:_:)` in v1.8: static methods avoid colliding with stdlib operator overloads, keep the witness-extraction shape uniform for SwiftInferProperties' RefactorBridge, and let the bridge alias a user's existing `+` / `*` / `zero` / `one` / `negate()` at writeout time. A type whose ring operations *are* `+` and `*` (i.e. it's already `Numeric`) does not need Ring — it gets the stronger stdlib coverage. Ring is for the carriers whose ring operations are named something else (`Matrix.multiplied(by:)`, `Polynomial.adding(_:)`, modular `combined(_:)`).

### Why `negate(_:)` (not derived from `zero` + subtraction)

The additive inverse is given explicitly as `negate(_:)` rather than implied through a `subtract` requirement, mirroring `Group.inverse(_:)`. This keeps the inverse laws single-sample and lets the bridge map a user's `negated()` / unary-`-` / `inverse()` directly. Subtraction is recoverable as `add(a, negate(b))` if a later law needs it; none of the eleven do.

### Derived laws left untested (Heuristic tier candidates)

Two facts are *theorems* of the ring axioms, not independent axioms:

- **Zero annihilation**: `multiply(a, .zero) == .zero == multiply(.zero, a)`. Provable from distributivity + additive cancellation.
- **Sign of products**: `multiply(negate(a), b) == negate(multiply(a, b))`.

The kit tests zero-annihilation for stdlib `Numeric` (it's cheap insurance against a broken concrete `*`). For kit-defined Ring these are derivable, so v1.10 ships them **not at all** in the Strict set — but they are the natural first occupants of a `Heuristic`-tier "derived ring identities" block if post-release dogfooding shows users want belt-and-suspenders coverage on hand-written `multiply`. Flagged here, not built.

## What this cluster will NOT do

### Out of scope, reachable in a future cluster

1. **`CommutativeRing` / `Field`.** Commutative multiplication and multiplicative inverses are independent axes. A `CommutativeRing: Ring` adding `multiplyCommutativity`, and a `Field: CommutativeRing` adding multiplicative `inverse` + the `one != zero` non-triviality law, are natural follow-ups — land them when SwiftInferProperties infers those shapes (it does not today). Probably a v1.11 cluster.
2. **`Rng` (ring without unity).** Drop `one` and the two multiply-identity laws. Add only if a real carrier (some convolution algebras) demands it.
3. **Heuristic-tier derived identities** (zero annihilation, product-sign). Built only if dogfooding asks for them (see §"Derived laws").
4. **`Module` / `VectorSpace`** (a ring acting on an abelian group). Two-carrier structure; far past current demand. Out indefinitely unless a strong use case emerges.

### Permanently out of scope (kit-side)

5. **`DerivationStrategist` arms for Ring types.** Conforming to Ring composes existing values; it doesn't help *generate* them. The `.derived` priority list stays as-is.
6. **`--advisory` suggesting `: Ring`.** Structural inference of "this looks like a ring" is SwiftInferProperties' job, not the kit's syntactic advisory layer.

## Cross-repo coordination (SwiftInferProperties side, not v1.10 work)

Once v1.10.0 is released:

1. SwiftInferProperties bumps its `SwiftPropertyLaws` dep (currently `from: "2.5.0"`) to the release that contains Ring.
2. The RefactorBridge's ring arm — which today can detect the shape but emits a claim-only suggestion — becomes able to write `extension TypeName: Ring {}` with the `add` / `multiply` / `zero` / `one` / `negate` aliasing to the user's existing operation names (same writeout mechanism as the Semigroup/Monoid arms from v1.8).
3. The discovery plugin emits `checkRingPropertyLaws` on the next regeneration, and the eleven laws run on every CI thereafter.
4. SwiftInferProperties' PRD §5.4 row for Ring updates from "claim-only" to "kit-defined Ring."

These are SwiftInferProperties-side follow-ups, not v1.10 work.
